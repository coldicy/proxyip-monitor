1. 产品概述

Proxy Monitor 是一个用于长期监控、筛选并同步 Cloudflare 反代 IP / ProxyIP 的工具。 它会周期性地对节点执行真实 HTTPS 探测，计算 TCP、TLS、HTTP 回源延迟， 统计成功率与达标率，并将满足优质窗口条件的节点上传到 GitHub。

  • 支持纯 IP、域名、URL 列表源三类节点来源。
  • 支持官方 Cloudflare 探针与自定义源站探针共同计算平均延迟。
  • 支持按总延迟上限、成功率阈值、达标率阈值筛选优质节点。
  • 支持将优质节点自动或手动上传到 GitHub 仓库。
  • 支持删除、屏蔽、自动清理长期离线节点。
  • 每次检测的失败原因会随样本持久化，任意一次离线都可回溯原因。

2. 快速开始

  1. 点击右上角 ⚙️ 设置，在 节点列表 ip.txt 中填写节点。
  2. 如果你要筛选真实回源可用的 ProxyIP，建议添加 自定义源站探针。
  3. 设置 优质总延迟上限，例如 300、500、800，单位 ms。0 表示不限。
  4. 设置 成功率阈值 与 达标率阈值，取值 0 - 1，例如 0.9 或 1。
  5. 点击 💾 保存并重载节点。
  6. 等待检测完成后，使用筛选、复制、上传功能。

优质节点需要样本充足。若优质判定窗口为 10，则至少需要 10 次检测样本后，才会开始判定优质。

3. 节点列表格式

在 ⚙️ 设置 的 ip.txt 中，每行可以写一个节点来源：

# 这是注释，不会被解析
1.2.3.4
1.2.3.4:8443
example.com:443
https://example.com/proxyip-list.txt
  • 不写端口时，默认使用 443。
  • 域名会自动解析为 IPv4 地址后加入监控。
  • URL 列表源会被抓取，其内容每行继续按 IP / 域名 / IP:端口 规则解析。
  • 支持 # 注释。
  • 当前监控对象以 IPv4 为主，IPv6 不会进入主列表。

如果你填写的是 Cloudflare 官方 IP 段，通常适合检测 CloudflareIP； 如果你填写的是自建反代节点，则更需要配置自定义源站探针来验证真实回源能力。

4. 核心指标

指标含义
平均总延迟优质窗口内在线样本的总延迟平均值。总延迟 = 官方探针 + 所有自定义探针总延迟的平均值。
平均TCPTCP 建立连接耗时的平均值，对应 time_connect。
平均TLSTLS 握手耗时的平均值，约等于 time_appconnect - time_connect。
平均HTTP从 TLS 完成到收到首字节 / 开始回源响应的平均耗时，约等于 time_starttransfer - time_appconnect。
成功率优质窗口内在线次数 / 窗口大小。例如窗口为 10，其中 9 次在线，则成功率为 90%。
达标率优质窗口内“在线且总延迟 ≤ 上限”的次数 / 窗口大小。若优质总延迟上限为 0，则达标率等同于成功率。
优质节点样本数达到优质判定窗口，且成功率 ≥ 成功率阈值，达标率 ≥ 达标率阈值。

举例：优质窗口 10 次，总延迟上限 300ms，成功率阈值 0.9，达标率阈值 0.8。 某节点 10 次中 9 次在线，其中 8 次总延迟 ≤ 300ms，则：成功率 90%，达标率 80%，满足优质条件。

5. 探针分工

官方探针

  • 默认使用 https://www.cloudflare.com/cdn-cgi/trace。
  • 用于检测节点是否具备 Cloudflare 反代能力，并读取 colo、loc、ip（出口IP）等元数据。
  • 官方探针要求返回 Cloudflare trace 内容，否则记录失败原因“官方探针返回非 CF 内容”。
  • 官方探针提供 TCP / TLS / HTTP 基础延迟数据。

自定义源站探针

  • 用于检测真实回源业务是否可用。
  • 每个探针都必须成功，该次检测才会被认为在线。
  • 任一自定义探针失败，该次样本会记录精确原因，例如 自定义探针失败: https://xxx (预期200实际502)。
  • 支持设置期望 HTTP 状态码，例如 200、204、301。
  • 最终平均延迟会综合官方探针与所有自定义探针。

自定义探针 URL 必须可被 HTTPS 访问。系统会使用 --resolve 将探针域名强制解析到被测 IP:端口，从而测试该 IP 是否真正代理到你的源站。

6. 页面操作

顶部按钮

  • 📖 手册：打开本手册。
  • 📜 日志：查看运行日志。
  • ⚙️ 设置：配置运行参数、探针、节点列表与 GitHub。
  • ⏹ 中断：中断当前正在执行的批量检测。
  • ⚡ 立即检测：立即触发一次检测。
  • 📤 上传优质节点：立即上传当前优质节点到 GitHub。

表格列

  • 节点 (IP)：IP、端口、身份、地区（国旗）、数据中心、出口IP、最近检测时间与首次来源（纯IP / 域名 / 列表）。
  • 优质窗口延迟统计图：最近 N 次检测结果柱状图。
  • 平均总延迟 / TCP / TLS / HTTP：优质窗口内在线样本的平均值。
  • 达标率 / 成功率：优质窗口内的两个核心比例。
  • 状态：优质、达标、在线、离线（离线徽章悬浮可查看最近一次失败原因）。
  • 操作：复制单个节点或删除单个节点。

延迟柱状图与失败原因

  • 绿色：在线，且总延迟满足上限；若上限为 0，则在线即绿色。
  • 黄色：在线，但总延迟超过设定上限。
  • 红色：该次检测失败。悬浮可查看后端随样本记录的该次精确失败原因，例如： 不具备反代CF能力 (超时)、官方探针返回非 CF 内容 (不具备反代能力)、 自定义探针失败: https://xxx (预期200实际502)、检测异常: ...。
  • 失败原因与检测样本一起持久化在 history.json，因此历史红柱同样可回溯原因，无需依赖日志。
  • 悬浮同时展示该次各探针的 总 / TCP / TLS / HTTP 明细。

复制格式

IP:端口#地区 | 总延迟 | TCP | TLS | HTTP
1.2.3.4:443#SJC | 210ms | 90ms | 60ms | 60ms

📋 复制筛选节点 会复制当前筛选与排序后的节点列表。 若只想复制优质节点，可勾选 只看优质 后再复制。

7. 设置说明

优质总延迟上限 (ms)达标判断上限。0 表示不限延迟，此时达标率等同于成功率。

成功率阈值 (0-1)优质节点要求的最小成功率，例如 0.9 表示 90%。
达标率阈值 (0-1)优质节点要求的最小达标率，例如 0.8 表示 80%。
自定义源站探针可配置多个真实源站 URL 与期望状态码。全部成功才算在线。

后端要求达标率阈值不能高于成功率阈值。若设置过高，会自动调整为不超过成功率阈值。

8. GitHub 同步

配置 GitHub 后，系统会将当前优质节点上传到指定仓库。上传文件格式如下：

# ProxyIP quality list (auto uploaded by proxy-monitor VERSION)
# updated: 2026-01-01T00:00:00.000Z
# nodes: 3
1.2.3.4:443#SJC | 210ms | 90ms | 60ms | 60ms
5.6.7.8:443#FRA | 180ms | 80ms | 50ms | 50ms
  • 前缀_all.txt：全部优质节点。
  • 前缀_地区.txt：按最新地区拆分的优质节点。
  • 地区名会被转为小写并过滤特殊字符，例如 proxyip_sjc.txt。

上传方式：

  • 📤 上传优质节点：手动立即上传。
  • 优质列表变化时自动上传：每轮检测后，若优质列表内容变化则上传。
  • 定时上传周期：按固定周期上传。

9. 删除与屏蔽

  • 手动删除节点后，该节点会进入屏蔽记录，避免被 ip.txt 立即重新加入。
  • 自动清理长期离线节点后，也会进入屏蔽记录。
  • 在设置底部可查看被移除节点记录。
  • 清空记录 会解除全部屏蔽，节点可重新被发现。

10. 常见问题

为什么节点在线但不是优质？

  • 样本数还未达到优质判定窗口。
  • 成功率低于阈值。
  • 达标率低于阈值。
  • 总延迟多次超过优质总延迟上限。

为什么显示“官方探针返回非 CF 内容”？

通常表示该 IP:端口 当前没有返回 Cloudflare trace，可能不是有效的 CloudflareIP， 或端口、协议、Host 配置不正确。

为什么自定义探针失败？

  • 源站不可用或响应超时。
  • 期望状态码不正确，例如源站实际返回 204，但你写了 200。
  • HTTPS 证书或 TLS 握手失败。
  • 探针路径需要鉴权、跳转或返回非预期内容。

离线原因从哪里看？

悬浮红色失败柱或“离线”徽章即可查看。原因由后端在每次检测时写入样本（failReason 字段）并持久化， 因此任何一次历史离线都能回溯精确原因，不再依赖日志是否被滚动覆盖。

为什么 GitHub 上传失败？

  • Token 无效、过期或权限不足。
  • 仓库名填写错误，应为 owner/repo。
  • 分支不存在。
  • 当前没有优质节点可上传。

如何只复制优质节点？

勾选筛选区的 只看优质，然后点击 📋 复制筛选节点。

为什么删除后的节点又出现了？

如果你清空了屏蔽记录，节点会重新被 ip.txt / 域名 / 列表源发现。 若不想让它再次出现，请同时从 ip.txt 或列表源中移除。

12. 最佳实践

  • 监测间隔建议 60 - 300 秒，不建议过于频繁。
  • 单次超时建议 4 - 8 秒，视网络环境调整。
  • 优质判定窗口建议 10 - 30 次，窗口越大结果越稳定。
  • 成功率阈值建议 0.9 - 1，达标率阈值建议 0.8 - 1。
  • 如果用于真实业务，请务必配置自定义源站探针。
  • 自定义探针建议使用轻量、稳定、无鉴权的健康检查路径。
  • 不要配置过多自定义探针，否则会显著增加每轮检测时间。
  • 上传 GitHub 前，先确认 Token 权限最小可用，避免泄露高权限凭据。
